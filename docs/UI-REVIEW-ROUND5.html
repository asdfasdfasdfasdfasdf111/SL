2. 逐条详情

P0「联机」整页空白 —— 没有任何内容，也没有任何解释

截图读数：导航栏「联机」处于选中态（蓝色胶囊），但下方内容区自 y≈110 到窗口底部约 470pt 全是纯背景色， 没有任何元素：没有大标题、没有加载指示、没有「暂无内容」、没有引导按钮。 对比同窗口的其它页：下载页有「正式版」大标题与搜索框，游戏页有「游戏检索中.」加载文案， 下载详情页有「没有进行中的下载」空态文案 —— 只有联机页是彻底的空白。

代码定位：qwq/Features/ModBrowser/CategoryContentView.swift:244-251

} else if category.name == "联机" {
    ScrollView {
        LazyVGrid(columns: [GridItem(.adaptive(minimum: 280))], spacing: 20) { }
            .padding(.horizontal, 32)
            .padding(.vertical, 32)
    }
    .frame(maxWidth: .infinity, maxHeight: .infinity)
    .background(Color.clear)
}

网格的 content 闭包 { } 是空的：既没有数据源，也没有占位视图。 下面 :264-269 的 else 兜底分支同样是一个空 LazyVGrid。

HIG 依据：macOS 平台的「内容呈现」要求页面在无内容时给出可解释的状态，而不是留空； 本工程自己在下载页已经遵循了这条（「没有进行中的下载」），联机页是唯一漏掉的。

建议改法（只改 UI 层，本轮不动代码）
① 若该功能未实现：把空白换成明确的状态说明 —— 居中一个图标 + 一句 「联机功能尚未开放」+ 一行次要说明（例如「当前版本仅支持单机启动」）， 并给出下一步动作（如「查看下载」按钮）。
② 若已有数据源只是被注释掉了：恢复取数，并把空态与加载态按下载页同一套文案风格补齐 （加载中 → 骨架/转圈；空 → 说明 + 动作）。
③ 若短期不打算做：把「联机」从导航里移除，避免把用户带到一个死页面。

P0启动页版面失衡：主操作挤在左上角小卡里，右侧 60% 恒为空白

截图读数：窗口 900×656；启动卡片占 x≈20–300（约 280pt 宽），卡片外的 x≈300–900（约 60% 宽度）与 y≈575 以下全部是背景色。卡内自上而下： 「当前版本: 1.20.1-Forge」（小号次要色）→ 皮肤头像（约 100×100）→ 玩家名「Player」 → 描边胶囊「选择皮肤」→ 描边胶囊「启动游戏」（卡内最宽元素，约 190pt）。
启动器的主操作是「启动游戏」，而它在窗口里占据的是信息层级最低的角落： 既不在视觉中心，也没有尺寸上的主次区分（和「选择皮肤」同为胶囊，只是更宽）。

代码定位：qwq/Features/ModBrowser/CategoryContentView.swift:238-239（启动页分支） → launchView；卡片与按钮尺寸见 qwq/Features/Launch/LaunchButton.swift:122 （.frame(width: buttonWidth, height: 50)）。

HIG 依据：macOS 布局规则要求主内容区被有效利用、且「主操作在视觉上应当显著」。 当前布局两项都不满足：60% 的窗口是死区，主操作与次要操作视觉权重接近。

建议改法
① 给启动卡一个随窗口伸缩的目标宽度（例如内容区宽度的 40%–50%，或干脆 两栏：左栏账户卡 + 右栏「最近实例 / 公告 / 快速入口」），把右侧空白变成有效信息区。
② 拉开主次：「启动游戏」做成实心强调色（当前为描边）并加大（高度 50 → 56/60）， 「选择皮肤」降级为文字按钮或次级描边。
③ 卡内垂直节奏收紧：当前「选择皮肤」到「启动游戏」之间有约 90pt 空档， 可按 12/16/24 的间距阶梯重排，避免卡身高而空。
④ 版本信息「当前版本: 1.20.1-Forge」提升为有标签的字段（如「实例」标签 + 版本胶囊）， 现在它是一行 11pt 的次要文字，用户很难判断「我在启动哪个实例」。

P1下载详情页：空态文案没有垂直居中，左侧指标卡高 530pt 只放 3 行

截图读数：左侧指标卡 x≈16–180、y≈118–650（高约 530pt），内部只有三组数据 （总进度 0.0% / 下载速度 0 B/s / 剩余文件 0），每组下面一条蓝色分隔线，三组只占到 y≈390， 卡下部约 260pt 是空的。右侧内容区里「没有进行中的下载」出现在 y≈169 —— 贴着内容区顶部， 而非在右侧区域垂直居中；它所在的横向位置也没有居中于 180–900 这段空间。

代码定位：详情页空态与指标卡在 qwq/Features/Download/DownloadDetailView.swift； 高度约束来自 qwq/Features/Download/DownloadDetailManager.swift 的三项进度字段。

HIG 依据：布局要求「空白区域应被有意识地使用」；空状态（empty state）应在 其所在区域内居中，并解释「为什么没有内容」以及「怎么让内容出现」。

建议改法
① 右侧空态改成区域内居中（Spacer/Spacer 或 .frame(maxWidth:.infinity, maxHeight:.infinity) 下居中）， 补一个次要图标（如 arrow.down.circle）与第二行说明「在下载页选择一个版本即可开始」。
② 指标卡改为「内容自适应高度」（不撑满），或把三项数据改为横向三列排布， 把省下的竖向空间留给下载任务列表。
③ 三项数值统一等宽数字字体，避免 0.0% / 0 B/s / 0 跳动时宽度抖动。

P1版本卡片信息量过低：只有「版本号 + 类型」，全列表长得一模一样

截图读数：内容区大标题「正式版」，右上角搜索框 placeholder 也是「搜索正式版...」。 卡片 3 列，每张约 220×110，仅含两行：版本号（如 26.1.1 / 1.21.11，大面积留白）+ 次要色「正式版」。 整屏 12 张卡片除版本号外完全一致：没有发布年份/日期、没有图标、没有「是否已安装」标记、 没有 Java 需求提示。用户要选版本时只能逐张读版本号。

代码定位：卡片由 qwq/Features/Game/ViewModels/DownloadCategoryViewModel.swift:507-514 的 makeMinecraftVersionItems 生成 —— 每项只填 id/name/subtitle，iconURL: nil、tags: []；

DownloadedItem(id: id, name: id, subtitle: displayTitle, iconURL: nil, tags: [])

即：卡片模板支持图标与标签，但数据源没有提供任何可展示的附加信息。

HIG 依据：列表/集合应让用户在不进入详情的前提下完成筛选；同类条目之间需要可区分的 次要信息（日期、状态、来源）。

建议改法（只给方案，本轮不改）
① 卡片补第二行信息：发布时间（Mojang 清单里已有 releaseTime， MinecraftVersionInfo 里可加字段）或「需要 Java N」（工程已有 JavaRequirement.minimumMajor(forMinecraftVersion:) 可直接算）。
② 卡片右上角加状态徽标：已安装 / 当前使用（数据来自 GameDirectoryScanner.localOwnedVersions）。
③ 搜索框 placeholder 改为「搜索版本号」（不要重复标题「正式版」），并在有输入时提供清除按钮。
④ 建议按年份分组加分组头（如「2026」「2025」），当前 12 张同质卡片没有锚点。

P1个性化色板 8 个色块断成 7+1，第 8 个孤立成一行

截图读数：标题「选择强调色」+ 副标题「将用于分类高亮和按钮」。 下面 8 个色块：蓝/紫/粉/红/橙/黄/绿 一行 7 个，第 8 个「灰色」单独出现在第二行左侧。 选中项（蓝色）用白色描边环 + 外发光表示 —— 这一点是正确的（不只靠颜色区分选中态）。 色块下方都有中文色名。

代码定位：qwq/Features/Settings/ColorPickerView.swift + qwq/Features/Settings/ThemeManager.swift。

HIG 依据：分组应当是完整、可预期的（避免 7+1 这种「差一个换行」的排布）； 颜色选择必须同时提供非颜色的标识 —— 本页已满足（有选环 + 色名）。

建议改法
① 改成 4×2 或 8 个等分的自适应网格（LazyVGrid(columns: .adaptive(minimum: 72))）， 使任意窗口宽度下都不出现孤块。
② 或把「灰色/无强调色」语义单独拆出（它是「关闭强调色」而不是一个颜色）， 放到色板右侧作为独立开关，色板只保留 7 个颜色。

P1启动按钮：进度填充与底色几乎分不出来、无百分比；且「取消」只停界面不停流程

截图读数：胶囊按钮宽约 480pt、高 50pt；进度以「左侧填色 / 右侧底色」表达。 检查阶段填充约 45%，填充色淡蓝（约 #A8C3E0）、底色浅灰（约 #C9C9C9），两者明度差很小； 启动阶段填充约 97%，右侧只剩一条 3–4pt 的未填充细缝 —— 这个宽度容易被读成渲染瑕疵而不是进度。 全阶段均没有百分比数字，也没有已用/剩余时间。

代码定位：qwq/Features/Launch/LaunchButton.swift —— 填充宽度与圆角裁切见 :122 附近（.frame(width: buttonWidth, height: 50) + .mask(RoundedRectangle(cornerRadius: 25))）；阶段切换见 beginPhaseTransition(to:)（:41-54，800ms 锁定 + 排队）。
按钮自身 .disabled(isLaunching)（:130）。

关于「能不能取消」——这里更正一个从截图容易得出的错误结论： 单看按钮会以为启动期间无法取消，但代码里 CloseSessionButton.swift:25 是 if isLaunching || hasRunningSessions { … }，即启动期间电源/关闭按钮是显示的， 点击走 LaunchCoordinator.handlePowerTap。真正的缺口在逻辑层而非界面层： 该分支在「尚无 live process、尚未 .launcherReady」时只重置界面状态与相位， 并不终止正在进行的启动流程 —— 于是「准备中/检查完整性/下载补全」阶段点取消， 界面回到 idle，但几秒后游戏仍会被拉起。这一条已由逻辑层深读独立记录 （见 docs/ROUND5-DEFERRED-ISOLATION.md 同批的启动取消链路问题）。

HIG 依据：进度指示应在一眼可读的距离上区分已完成/未完成；耗时操作必须提供真正生效的取消。

建议改法
① 填充色换成强调色的高饱和版本（theme.accentColor 约 0.85 不透明度）， 底色降到 Color.secondary.opacity(0.18)，把明度差拉开； 或把进度条移到按钮下方（细条 + 圆角），按钮只承载文案与点击。
② 文案加百分比并使用等宽数字：「正在检查游戏完整性 45%」，避免数字跳动时宽度抖动。
③ 进度 ≥95% 时不要再画那条细缝（让填充铺满 + 文案表达"即将完成"），或把未填充区固定为最小可见宽度（如 ≥8pt）。
④ 取消链路需要与逻辑层一起改：LaunchSessionManager 增「已请求取消」标志， 让启动流程在每个 await 点检查并尽早中止；这一步属行为变更，建议单独立项。

P2拖入文件的高亮只有一圈细边框，没有文案或图标

截图读数：拖拽悬停时窗口四周出现一圈蓝色描边（约 3pt），页面内容不变、不加蒙层， 没有「松开以安装」「将安装到：<实例名>」之类的文案。

代码定位：qwq/App/ContentView.swift 的 .onDrop + qwq/App/ViewModels/DropInstallCoordinator.swift（分流决策），高亮样式在根视图 overlay。

HIG 依据：拖放目标必须在悬停时明确表示接受并可预览结果；仅描边不足以传达「会发生什么」。

建议改法：描边内叠加一层 theme.accentColor.opacity(0.06) 蒙层 + 居中一行文案（如「松开即安装到 1.20.1-Forge」），并在文案下方小字说明「.jar → 模组，.zip/.mrpack → 整合包」。

P2错误提示：两个关闭入口、文案不含补救动作

截图读数：卡片左侧红色圆形叉号，标题「错误」，正文 「模组安装失败：无法连接下载源」，下方一个「确定」小按钮，右上角还有一个 ×。 两个控件做的是同一件事（关闭），但一个叫「确定」一个没有标签。

代码定位：qwq/UI/Notices/NoticeCenter.swift + NoticeOverlay.swift； 本条与 qwq/Features/ModBrowser/CategoryContentView.swift／ DropInstallCoordinator 里的错误投递点有关（失败原因字符串在此拼接）。

同组另两张可以对照：07-notice-3warning.png 的「注意」条写的是 「皮肤已保存，资源包注入失败」—— 把部分成功如实说清楚，这是本工程做得好的地方； 07-notice-1info.png / -2success.png 同构。也就是说本条问题只在 「缺补救动作 + 两个关闭入口」，不在信息传达本身。

HIG 依据：警示/错误信息应说明用户能做什么；同一结果不应有两个语义重复的控件。

建议改法
① 正文补一行可执行建议，例如「请到『个性化 → 下载源』切换到镜像源后重试」， 并直接给一个「重试」按钮（工程已有下载源切换能力）。
② 去掉「确定」，只留 ×；或反之 —— 保留「确定」并隐藏 ×。
③ 错误原因做两级：一句话结论 + 可展开的详情（当前把原始错误直接拼在标题行后）。

P2品牌命名不一致：界面写「SL启动器」，工程/Bundle 叫 qwq

截图读数：所有页面左上角大标题是 SL启动器（HomeHeader.swift:30 的 Text("SL启动器")），而工程名、target 名、Bundle 名是 qwq， 日志目录是 SL启动器，代码注释里还留着一批上游项目名（本轮已有专项清理）。

HIG 依据：产品命名应全应用一致（应用名、窗口标题、关于面板、日志目录）。

建议改法：确定唯一产品名，然后在三处对齐：① CFBundleDisplayName/CFBundleName； ② HomeHeader 大标题；③ 应用支持目录名（SharedConstants.applicationSupportURL） —— 注意第 ③ 项一改会让老用户的日志/配置搬家，需要做一次迁移或保留旧目录读取。

P2macOS 主菜单与偏好设置入口缺失

代码核查（不是看截图猜的）：全库检索 .commands { / CommandGroup / CommandMenu / keyboardShortcut / Settings { }（SwiftUI 设置场景） 零命中。也就是说：没有「偏好设置…」菜单项、没有 ⌘, 、没有 ⌘R/⌘W 之类的命令绑定， 全部操作只能靠鼠标点导航。

HIG 依据：macOS 平台规则要求应用提供标准菜单栏命令与偏好设置入口（Settings 场景）， 且常用操作应有键盘快捷键。

建议改法：在 qwqApp.swift 的 WindowGroup 后加 ① Settings { ... } 场景（把「个性化」里的强调色、下载源等搬进去或做镜像入口）； ② .commands { CommandGroup(replacing: .newItem) { } ... } 加「切换分类 ⌘1…⌘6」 「刷新 ⌘R」「显示日志 ⌘L」等。这一步是纯增量，风险低。

3. 动画与动效专项（"它的动画效果是怎么样的"）

下表把界面里实际接线的动画逐个列出来（参数取自代码，非估算），并给出评价。 判断依据：这条动画是否被真的读到、是否有存在的理由、参数是否与工程内其它动画一致。

动画点实际参数（代码原文）评价
启动按钮阶段切换 LaunchButton.swift:41-54
phaseSpring + 800ms 锁定；锁定期间新相位排队，解锁后播最新		 接线正确且考虑周全。锁定 800ms 等于 spring(0.5) 的视觉完播时长，避免快速相位跳变时动画叠加/抖闪；排队只保留最后目标，不会补播中间态。
启动按钮点击回弹 punchySpring = spring(response 0.6, damping 0.5, blend 0.2) 合理。scaleTask 可取消（视图销毁后不写已释放 State storage），是防 UAF 的正确写法。
侧栏子项入场 GameViews.swift:70-77：延迟 0.3s 后 spring(0.5, 0.7) 把三个子项 opacity 0→1 可用，但批量同时淡入没有错落感；建议给三个子项加 0.03–0.05s 的递进延迟（stagger），视觉上更像"展开"而不是"亮起来"。
分类切换（内容区） GameViews.swift:283-297：0.12s 淡出到 opacity 0.6 + offset 8 → 0.08s 后 0.18s 淡入 "淡出 0.12 / 停顿 0.08 / 淡入 0.18" 是合理的快节奏；注意 offset 只在纵向（8pt），横向无位移，故切换时没有方向感，建议与画布拖拽方向一致。
分类画布换页 NavigationState.swift:37-43：spring(response 0.6, damping 0.65, blend 0.15)；阈值 25% 画布宽；最小拖拽 20pt 参数与手感匹配（0.25 阈值 + 弹簧是常见组合）。评价：合理，无需改。
强调色系弹簧 AnimationExtensions.swift：explosiveSpring(0.7,0.5,0.2)、exaggeratedSpring(0.9,0.4,0.35)、punchySpring(0.6,0.5,0.2) 三档弹簧命名与参数自洽，但 exaggeratedSpring 的 dampingFraction 0.4 明显偏弹（会过冲约 3 次），用于会话日志卡升起会造成"晃"。建议日志卡这类大块元素改用 0.6–0.7 阻尼。
游戏页扫描时序 GameCategoryView.swift:103-127：10s 超时判定（0.8s 动画退化）、卡片出现 0.8s、载入结束 0.4s 合理。特别是"迟到的扫描结果按 scanTimedOut 丢弃"解决了超时后退化态被覆盖的问题；省略号计时器 0.5s/帧也符合常规。
提示条（Notice） UI/Notices/NoticeOverlay.swift：入场/退场 .move(edge:.top).combined(with:.opacity)（本轮修正了接线） 已修。此前 transition 挂在错误层级，导致换消息时只有淡入没有位移动画。

4. 不能判断的部分（这一节不能省）

4.1 截图里像 bug、经核实不是缺陷的（已逐条排除）

  • 赞助页两张卡片显示「图片缺失」 —— 截图里是灰底占位 + "图片缺失"。核对：资源是 qwq/zanzhu1.png / qwq/zanzhu2.png，工程用 PBXFileSystemSynchronizedRootGroup 同步整个 qwq/ 目录，构建产物 qwq.app/Contents/Resources/ 里确实存在这两个文件。离屏渲染器的 NSImage(named:) 找的是渲染器自己的 bundle，所以取不到 —— 渲染假象。
  • 下载页侧栏「游戏」下方那块空的蓝色高亮 —— 是展开后的三个子项容器，其 subItemOpacity 初值为 0，靠 onAppear 里延迟 0.3s 的淡入拉到 1； 离屏渲染不触发 onAppear，故渲染成空块。非缺陷（本轮已顺手清掉同处一个死参数）。
  • 药丸提示（06-pill-*.png）整块空白 —— 同一原因：入场 opacity 初值 0。 非缺陷。
  • 05-close-button-hidden / -launching / -running 三张是纯白画面 —— 这三张是关闭按钮的隔离渲染， 在默认浅色外观下按钮与背景同为白色，整组不可用。该按钮的显隐已改用代码核对： CloseSessionButton.swift:25 if isLaunching || hasRunningSessions —— 启动期间它是显示的（详见第 2 节启动按钮那条的「更正」）。
  • 启动按钮截图是浅灰底黑字（04-launch-button-1idle.png），而窗口截图里同一个按钮是深底白字 —— 渲染器没有设置 NSApp.appearance = .darkAqua（已核对 /tmp/uir/main.swift），隔离渲染的单控件落到默认浅色外观。 因此 04/05/06 这三组截图的颜色不可采信，只有几何与文字可信。

4.2 必须真机操作或录屏才能判定的

  • 动画的实际手感（弹簧过冲、drop 高亮的时延、分类切换的跟手程度）：离屏渲染是静态单帧， 本文只能核对"参数与接线"，无法评价"跑起来是否顺"。建议用 ⌘⇧5 录一段 10 秒的屏幕录制（切换分类 → 拖入一个 jar → 点启动）， 我能据此把动效评价补成"逐帧"级别。
  • 真实窗口下的对比度与可读性：深浅外观、Display P3 / 非 Retina 屏上的表现需要真机看。 第 2 节里"进度填充对比度低"这条在真机上可能与截图不同，建议一并录屏。
  • 键盘导航与 VoiceOver：需要辅助功能权限，无法在离屏渲染中判断。
  • 本次截图集未覆盖的界面：模组详情页（ModDetailView，含页面滑入 entryScale 0.85 → 1 的入场动画）、游戏运行日志卡（SessionLogCardView， 由 exaggeratedSpring 0.9/0.4 驱动）、以及各类弹窗（模组安装目标选择、整合包位置选择）。 这三处没有做视觉评审，只做了代码级核对（动画参数已列入第 3 节）。 要补评需要把渲染器扩展到这些界面，或提供真机截图。

4.3 HIG 规则库未覆盖、按通用设计判断的（已标注，不冒充官方依据）

  • 「启动卡宽度应随窗口伸缩」—— 属于布局常识，HIG macOS 布局章节给的是原则而非具体尺寸。
  • 「版本卡片建议补发布日期」—— 信息密度取舍，非条文要求。
